# 0004 引擎自己写：执行图加令牌、操作都是命令，两种画法编译成同一种执行图

状态：引擎决定继续采纳；双画法及转换部分已被 0007 取代（2026-10-13）
日期：2026-10-13
关联：T-001、T-002

## 背景

审批服务要同时支持钉钉式的树形画法和按 BPMN 画的自由画布，中国式审批规则要做全（会签、或签、票签、退回到任意节点、加签、委托……），以后还要作为平台里的一个微服务扩展。开源引擎里，Elsa 偏通用自动化编排，Camunda、Flowable 是 Java，CCFlow 是 GPL；中国式审批规则在它们上面都要深度定制。

## 决定

- 引擎自己写，放在单独的 `ApprovalService.Engine` 项目里，只引用 Contracts，不碰数据库、文件、网络。
- **执行图**：两种画法发布时都编译成同一种执行图（节点、连线、网关），引擎只认执行图。钉钉式可以一键转成自由画布，反过来不行。
- **令牌**：运行时用令牌标记走到哪，并行、包容、回路、子流程都用这一套。
- **命令和事件**：每个操作是一条命令，经引擎的同一个入口处理，算出新状态并产生事件；事件写进只追加的操作记录，回调、消息、统计都从事件来。
- **纯**：时间、ID、组织架构查询结果由调用方传入，同样的输入一定得到同样的结果，预览和测试模式在内存里跑同一个引擎。
- 自由画布按 BPMN 2.0 的常用子集：开始和结束、用户任务、排他、包容、并行网关、子流程、服务任务；导出为 BPMN 2.0 文件加本系统的扩展信息，只导入本系统导出的文件。

## 备选方案

- 用 Elsa 3：要在它上面实现全部中国式审批规则，绕的路比自己写多，升级也受它牵制。
- 只做钉钉式：画不出返工重审这种回路，用户要求两种都做。
- 完整的事件溯源（状态完全由事件重放得出）：复杂度高；现在存状态加只追加的事件，事件够用来核对和重放检查。

## 影响

- 第 4 节需求清单的每条规则都要有场景检查；另外随机生成流程图和操作顺序做稳健性检查。
- 节点类型、审批人来源、多人审批方式、函数等做成扩展点（docs/architecture.md）。
