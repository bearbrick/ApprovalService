# 0010 明确业务系统四类出站钩子的 HTTP 协议

状态：提议
日期：2026-10-20
关联：T-006

## 背景

设计书第 12、13 节确定审批服务按需调用业务系统的取数、校验、取人和业务动作接口，均经出站适配层、双方验签、默认 5 秒超时。但尚未规定 URL 拼接、HTTP 方法、请求与响应 JSON、响应验签和超时后的状态。协议一旦公开给业务系统就难以回退；T-006 在未确认前不能猜测这些语义。

## 决定（待确认）

接入应用分别登记四个完整的 HTTPS 绝对地址；开发环境可登记 HTTP 地址。审批服务对所需地址发送 `POST`，JSON 属性小驼峰。`X-Approval-Signature` 是对原始 UTF-8 请求体的 HMAC-SHA256，格式与结果回调相同；同时传 `X-Request-Id`，业务系统原样带回。业务系统响应也用同一个密钥对原始响应体签名，审批服务验签后才使用。接口不在登记地址后拼接路径或查询参数。默认 5 秒超时，只有 HTTP 2xx、签名有效且响应 JSON 合法才视为成功。

| 钩子 | 请求体 | 成功响应体 |
| --- | --- | --- |
| 取数 | `{ "flowCode", "businessKey", "requestId" }` | `{ "data": { … }, "title": "可选", "detailUrl": "可选" }`；`data` 必须是对象 |
| 校验 | `{ "phase": "start/approve", "flowCode", "businessKey", "instanceId": "可选", "taskId": "可选", "actor", "data" }` | `{ "allowed": true/false, "reason": "不允许时必填" }`；不允许时给用户显示原因且不写审批状态 |
| 取人 | `{ "flowCode", "businessKey", "nodeId", "sourceValue": "可选", "initiator", "data" }` | `{ "userIds": ["业务系统用户 ID", …] }`；服务端经接入应用绑定或工号解析为在职内部人员，空列表交给节点的无审批人策略 |
| 业务动作 | `{ "eventId", "actionCode", "instanceId", "flowCode", "businessKey", "data" }` | `{ "success": true/false, "message": "可选", "result": { … } }`；业务系统按 `eventId` 幂等，失败由持久待发队列重试 |

取数和校验在审批事务之前同步调用；取人也只在进入相应节点前调用。业务动作在事务提交后由待发队列调用。超时、网络错误、非 2xx、响应签名或格式错误均返回可辨认的业务钩子错误；同步钩子不写入部分审批结果。签名密钥只加密存库，请求与响应正文不得出现在普通日志里。

## 备选方案

用 GET 和查询参数取数较易接入旧系统，但业务单号、用户 ID 易进入代理访问日志，也无法为各类请求统一签名。让每个业务系统自定义 JSON 映射会增加可配置脚本和兼容性风险。只给请求签名、不验响应无法兑现“双方验签”，因此暂不采用。

## 影响

确认后在后端 Contracts、`docs/contracts.md`、设计书第 12、13 节同步精确格式，再实现四类钩子和假业务系统场景检查；调用端 SDK 的相应模型由 T-016 同步。当前提议不改变已上线接口，尚未实施、也不用于 T-006 验收勾选。
