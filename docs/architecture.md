# 架构

设计说明见设计书 [docs/design/approval-service-design.html](design/approval-service-design.html)（第 2、9、10 节），硬性规则见 [AGENTS.md](../AGENTS.md)。本文写代码怎么组织、新东西放哪。

## 总览

```
业务系统（Web、WinForms）──开放接口 / SDK──┐
审批人（电脑、手机网页）──审批中心 API────┤
流程管理员（浏览器）──管理 API──────────┤
                                       ▼
                         审批流服务（ASP.NET Core，单进程）
                         Api → Application → Domain → Engine
                                    ↓
                             Infrastructure：数据库、附件、消息、出站适配层、后台任务
                                    ↓
                     业务系统的回调、钩子接口；邮件（以后企业微信、钉钉）
```

仓库分成三个互不引用的部分：`frontend/`（网页）、`backend/`（服务端）、`client/`（SDK 和示例业务系统），只通过 HTTP 交互。

## 后端分层

依赖只能从上往下：Contracts ← Engine ← Domain ← Application ← Infrastructure ← Api。后端检查程序的 `ArchitectureChecks` 会核对项目引用和禁止的 using。

| 项目 | 职责 | 可以引用 | 不能碰 |
| --- | --- | --- | --- |
| `ApprovalService.Contracts` | 对外契约：接口路径、HTTP 头、错误码、请求和响应体、流程定义 JSON | 无 | 任何项目和包 |
| `ApprovalService.Engine` | 引擎核心：执行图、令牌、命令、事件、审批规则 | Contracts | 任何包；数据库、文件、网络、依赖注入、配置、日志 |
| `ApprovalService.Domain` | 领域层：实体（`XxxEntity`）、领域规则（`XxxRules`）、仓储接口（`IXxxRepository`）、`UserFriendlyException` | Contracts、Engine | 任何包；EF Core、ASP.NET Core |
| `ApprovalService.Application` | 应用层：应用服务（`IXxxAppService`）、输入输出模型（`XxxDto`）、对基础设施的抽象 | Contracts、Engine、Domain | EF Core、ASP.NET Core |
| `ApprovalService.Infrastructure` | 基础设施层：EF Core 和三种数据库、仓储实现、附件存储、消息渠道、出站适配层、后台任务 | 以上全部 | — |
| `ApprovalService.Api` | 接口层：路由（`XxxEndpoints`）、鉴权、错误格式、请求 ID、组装（`Program`） | Contracts、Domain、Application、Infrastructure | 直接访问数据库 |

新功能的落点：

- 流程怎么走、找谁审、几个人怎么审 → 引擎核心。
- 其他业务规则（委托是否生效、编号怎么生成……）→ 领域层。
- 用例（权限和范围检查、调引擎、存库、记操作日志、转成 Dto）→ 应用层的 `XxxAppService`，在 `AddApprovalApplication` 登记。
- 数据库、文件、邮件、HTTP 出站 → 基础设施层，在 `AddApprovalInfrastructure` 登记。
- 路由 → 接口层的 `XxxEndpoints`，处理函数一般一行：调应用服务。

## 业务模块

`CenterOpinionAppService` 从已验证 JWT 范围提取内部人员 ID，按人隔离常用意见；`ICenterOpinionRepository` 在基础设施层用串行化事务控制每人 30 条上限。嵌入会话仅可读，写请求在应用层拒绝。意见正文不进入审批实例，只有用户选择并提交既有任务动作时才成为该次操作意见。

应用层、领域层、基础设施层都按同样的模块分文件夹：

| 模块 | 内容 | 设计书 |
| --- | --- | --- |
| `Flows` | 流程、流程版本、自由画布设计 JSON、编译成执行图、发布校验、导入导出 | 第 3、5 节 |
| `Runtime` | 审批单、任务、命令处理、操作记录、委托、审批矩阵、工作日历 | 第 4、9 节 |
| `Organization` | 部门、人员、角色、岗位职级、上下级、分管关系、业务系统绑定、推送变更 | 第 11 节 |
| `Identity` | 账号、登录、嵌入令牌、权限 | 第 11 节 |
| `Integration` | 接入应用、API Key、回调、钩子、出站适配层、待发队列 | 第 12 节 |
| `Notifications` | 消息渠道（邮件、站内）、提醒规则、待办汇总 | 第 6 节 |
| `Notifications/Calendar` | 纯工作日历规则：周末、节假日与调休覆盖、指定时区投影；按默认 09:00–18:00 或调用方配置的工作时段累计节点分钟时限，通知模块负责写入任务期限 | 第 4、6 节 |
| `Files` | 附件存储（本地、MinIO / S3）、权限检查、清理 | 第 9 节 |
| `Printing` | 审批单 PDF | 第 7 节 |
| `Reporting` | 跨期事实读取、管理范围内的报表查询与后续汇总 | 第 8 节、ADR 0019 |
| `Services` | 服务自身的信息（骨架已有） | — |

模块之间只通过接口调用，以后哪个模块要拆成平台的公共服务（消息中心、文件服务、统一认证、主数据）都好拆。

`Organization` 用 EF 保存部门、人员、多部门与角色关系、每个接入应用的外部 ID 绑定以及逐次变更审计。CSV/XLSX 文件在 API 边界解析为相同的 `OrganizationImportBatch`，可同时含部门、人员、所属关系和外部人员/部门绑定。Domain 一次检查重复工号与部门编码、数据库列宽、缺失引用、层级环和主部门唯一性；正式写入在可串行化事务内按当前组织快照重新校验，避免预览与保存之间的并发变更。接入应用 API Key 只能推送、绑定本应用可信来源的记录；跨来源绑定由本地组织管理员确认。`IOrganizationLookupAppService` 在一致读事务中提供数据库生成的找人快照，不接受调用方自造的组织快照。嵌入签发另用严格的本应用绑定查询，不能按全局工号回退。已采纳的 ADR 0013 要求开放任务接口的人员身份仅由当前接入应用的在职绑定解析，不按全局工号回退。

`Identity` 在 Application 暴露账号、刷新轮换、改密和一次性嵌入交换用例，Infrastructure 保存密码摘要与令牌摘要并签发短期 JWT。API 验签后回库核对在职状态、账号版本与嵌入会话的应用/外部用户绑定及应用身份代际。可信人员离职、复职和外部人员绑定换人时，组织写入事务单调递增受影响账号的令牌版本；一次性嵌入令牌记录签发版本，兑换时也核对，因此状态恢复不能让旧令牌复活。`ClientAppAppService` 的启停和密钥轮换用例通过单条条件更新递增 `ClientApp.AuthGeneration`；新嵌入 JWT、刷新令牌和一次性令牌记录签发代际，兑换、刷新及每次访问都核对当前启用应用和绑定，旧数据库嵌入令牌缺失代际时拒绝。应用停用再启用或轮换密钥都不能使旧嵌入会话复活，本地会话不带应用代际；受保护的管理 HTTP 入口已接通，实际变更在同一事务留不含密钥的审计记录。首次登录令牌只能改密。首位组织管理员由服务器本机一次性交互式命令初始化，Infrastructure 在串行化事务内创建或选取人员、开通需改密账号并授予角色，不提供匿名 HTTP 引导。管理授权每次查当前 `organization-admin` 角色并只允许本地密码会话；嵌入会话刷新也保留 `clientAppCode`，不能升级管理权限。审批中心后续 T-011 还须按嵌入会话的 `clientAppCode` 限制查询、详情、操作和附件下载到所属应用审批单。

`Center` 将已验证 JWT 的人员与嵌入应用范围作为独立可信输入，在 `ICenterQueryRepository` 内先按待办或持久参与者关系过滤，再计数、分页及加载详情。字段内容搜索分批读取这一授权集合，复用领域层可见字段裁剪规则后才确定命中、总数与分页；不查询原始 JSON 中的隐藏值。只读查询在一致读事务中关联固定发布版本、任务和事件；普通与保密流程均不在这个入口给管理员或额外查看人自动授权。应用层只投影可见字段和安全事件摘要，明细隐藏列与私人草稿不会借原始 JSON 返回。`CenterReadCursors` 按人员和审批单持久记录已读活动序号；列表读取同一事务内的新活动计算 `isUnread`，显式标记已读时重新核对保密参与关系和嵌入应用，再将游标单调推进至详情实际显示的序号（不超过数据库当前序号），避免详情后新活动被误读；本人操作或私人草稿不重新标未读。任务许可由纯引擎读取当前状态和固定发布图计算，写入时 `CenterActionAppService` 再次验证人员及嵌入应用范围、字段和节点许可，调用业务校验钩子后经统一运行时提交。批量同意逐项独立提交并返回结果，不提供发起或修改业务快照功能。桌面前端以本地登录 JWT 调用中心接口，令牌只在当前页面内存保存，到期前轮换；响应没有逐单操作许可时不展示可执行审批动作。`Api/Hosting` 同源托管前端构建物，默认给普通和静态响应 `frame-ancestors 'none'`，仅 `/embed/{clientAppCode}` 在应用层核对已启用应用及安全来源后放宽为 `'self'` 加登记来源。嵌入上下文接口从重验后的嵌入 JWT 读取应用，不接受路径或查询参数扩权；静态 HTML 不能绕过该策略，生产环境缺失构建入口会启动失败。

手写签名使用独立的不可变 `SignatureAssets`：应用层先限制原始 PNG 为 2 MiB，验证分块、CRC 与有界像素流，再按当前 JWT 人员保存原始内容和 SHA-256。个人签名只是可重复明确选择的资产，嵌入会话只能创建单次资产；审批操作先按本人核对资产归属，运行时将选用的资产 ID 冻结在审计事件与任务投影。引擎仅检查发布节点 `signatureRequired` 对成功推进命令的必签规则，不接触图片或数据库；必签任务不提供批量同意。已授权参与者读取历史签名时，应用层先复用审批单人员及嵌入应用授权，再核对事件或任务确实引用该资产，避免通过猜测 ID 访问其他人的个人图片。

`Administration/AdminConsoleAppService` 复用组织和接入应用仓储读取管理列表，API 对每个管理 GET 端点单独应用本地组织管理员策略。目录只映射部门、人员的展示字段，不提供联系方式；接入应用仓储查询只投影编码、名称、授权流程及启停状态，不装载密钥列。管理前端的令牌只存页面内存，首次登录改密前不读取管理数据；组织导入仍走现有预检和事务化审计写入。

流程管理身份基础由 `Domain/Runtime/FlowManagementAccessRules` 统一判断：在职本地组织管理员可管理全部流程；`flow-admin` 角色只覆盖人员直接加入的流程所属部门，无归属流程只由组织管理员管理。`Flow.AdministratorId` 继续作为运行期指定管理员的内部人员 ID，不单独授予编辑权限。`Infrastructure/Administration/FlowAdministratorIdentityReconciler` 由服务器本机一次性命令调用，先预览再按指纹提交；唯一匹配才改写，零匹配和多匹配存入待人工处理表，服务启动时不自动执行。`Administration/FlowManagementAppService` 负责草稿基础校验、发布编译和当前范围筛选，`Persistence/FlowManagementRepository` 在同一事务内复核角色/直属部门与草稿修订、追加不可变版本和安全审计。`Administration/FlowTransferAppService` 通过引擎的 BPMN 编解码器检查本服务兼容文件，预检只读、导入只写草稿；`Persistence/FlowTransferRepository` 在同一事务内复核管理范围后读取草稿或不可变发布版供导出。`Administration/FlowVersionAppService` 展示版本摘要并协调旧版恢复；`Persistence/FlowVersionRepository` 在同一事务里核对权限、草稿与发布指针后只复制旧定义为新草稿修订。

流程所属部门选项复用 `FlowManagementAppService` 与 `FlowManagementRepository`：仓储在同一可串行化读取事务中核对本地会话、在职状态和当前管理角色，再只投影可选现存部门的 ID/名称。组织管理员可取全部；部门流程管理员只取当前人员的直接部门关系，不沿组织树扩展。

## 引擎核心

引擎核心是单独的项目，只有流程执行的逻辑，预览流程、测试模式直接在内存里跑同一个引擎（设计书第 9 节）。

`Administration/FlowSimulationAppService` 创建会话前用现有流程管理服务复核本地 JWT 的组织管理员或该流程管理员权限，编译请求中未保存的完整草稿并校验假数据。各人工节点的假处理人只覆盖内存执行图的取人来源；原审批策略、网关和命令仍由 `EngineRuntime` 执行，自动动作与子流程必须显式给假结果。基础设施层有界内存容器只保存创建人、执行图、引擎状态及事件摘要，30 分钟闲置过期；读取、推进和删除每次重验流程权限。模拟服务不依赖真实运行仓储、待发队列或出站适配器。

- **执行图**：自由画布发布时编译成执行图（节点、连线、网关），引擎只认执行图。
- **定义与布局分离**：正式设计 JSON 的字段、节点与连线模型定义在 Contracts 的 `Flows/`；编译和发布校验放在 Engine 的 `Definitions/`。设计坐标只用于前端编辑，执行图只保留流转语义。BPMN 导出携带本服务扩展信息，导入仅接收本服务的兼容版本。
- **审批数据与表达式**：字段定义与只读详情排版属于流程版本；表达式解析、审批快照校验和金额计算放在 Engine 的 `Expressions/`，仅处理传入数据，不访问业务系统或修改业务单据。前端的字段与排版编辑器放在 `src/designer/data/`，由设计工作台接入。
- **审批中数据更新**：业务系统只能 PATCH 锁定发布定义中显式开放的字段；应用层核对所属接入应用和已绑定操作人，合并局部字段并重算公式及可信路由映射。引擎统一命令产生只追加的改前改后审计，运行仓储在同一乐观版本事务中保存新数据与事件；已到达任务不重派，后续节点按新快照计算。
- **退回与补充提交**：所属应用只可代表已绑定原发起人提交完整新数据；事务前按锁定定义校验、重算公式和当前可信找人映射，再通过统一引擎命令原子写入。引擎状态有独立的审批人填写当前值投影：成功推进时合并，退回重提时清空、补充时保留；事件历史不回写或删除。
- **自动动作结果**：业务动作成功后将可选 `result` 随原事件 ID 经引擎命令写入独立事件审计和运行投影；后续终态回调从已提交投影固定 `actionResults` 快照。原业务 `data` 不包含动作结果，重复领取已处理事件不重复调用业务端。
- **动作失败处理**：持久自动动作第十次失败后状态为 `needsAttention`，不再自动领取，保留原审批令牌、事件 ID、正文和失败类别。本地登录人员以当前在职工号匹配原事件审批单所属流程的 `AdministratorId`，通过后管理 API 以条件更新将原项排入一次人工重试；组织管理员角色不扩大流程范围。失败后再次待管理员处理，成功后按原事件 ID 幂等回写。
- **流程预览**：应用层复用发布流程授权、字段校验和当前可信组织快照，以相同纯引擎命令在内存中模拟同意与成功路径；业务接口找人仅在预计实际进入的节点调用。只返回预计路径和当前候选人员，不创建实例或待发项；真正到达节点时重新计算。
- **审批中心详情排版**：人员及嵌入应用授权先在查询仓储过滤，再以锁定版本和当前节点可见字段裁剪数据、字段定义、自定义分组和明细列宽；部分隐藏的分组不传原标题。金额大写只对已授权金额在应用投影中调用纯引擎转换，前端再次按已返回字段匹配排版项。嵌入原单模式在安全地址协议完成前回退自动排版。
- **令牌**：运行时用令牌标记走到哪。并行网关分叉生出几个令牌、汇合时等齐；包容网关只等真正走了的分支；回路、子流程用同一套机制。
- **命令和事件**：每个操作（同意、拒绝、退回、转交、加签、撤回、跳转……）是一条命令。引擎检查能不能做 → 算出新状态 → 产生事件；应用层把新状态和事件在一个事务里存下，事件写进操作记录（只追加、带校验值），回调、消息、统计都从事件来。
- **纯**：时间、ID、组织架构查询结果都由调用方传入，同样的输入一定得到同样的结果；不在引擎里调外部系统。
- **上限**：一张审批单最多推进 `EngineLimits.MaxStepsPerInstance` 步，子流程最多嵌套 `EngineLimits.MaxSubprocessDepth` 层。
- **检查**：设计书第 4 节需求清单每条至少一个场景检查；另外随机生成流程图和操作顺序反复跑，找卡死和重复推进。
- **审批人和多人规则**：`Assignees/IAssigneeResolver` 消费调用方在节点到达时提供的组织、审批数据、矩阵命中及业务接口预取结果，不直接查询数据库或调用 HTTP。岗位与职级各有一个来源编码，合计 15 个编码覆盖设计书 14 类来源。缺人、本人、重复和停用的处理由节点配置决定；实际找人结果和预览不同则写事件。`Policies/IApprovalPolicy` 按任务快照计算依次、会签、或签、票签结果；票签使用比例及人员权重，不能达到门槛时提前拒绝。策略与解析器收到隔离副本，不能改写引擎输入。
- **审批操作与委托**：`Commands/` 的操作也经 `EngineRuntime.Execute` 入口。运行状态保存发起人、退回恢复位置、征询、暂存、催办间隔、动态加签、后续节点改派及撤销同意的短期恢复帧；状态副本与事件一起提交，失败命令不改调用方对象。节点可限制操作并要求意见，事件的审计信息带操作人、代理关系、意见和管理员原因。管理员不能直接跳到并行或包容汇合网关，避免缺少分支令牌。委托按调用方时间及流程范围只解析一层，原审批人仍有处理权；代理人为发起人时按节点本人审批规则处理。流程的退回走法和撤回限制在发起时写入状态快照。批量同意逐项走同一入口，应用层负责跨审批单事务；离职交接的多实例遍历及流程定义维护也由应用层负责。管理员权限和撤销审批通过的事实必须由应用层核实后传给引擎，不得直接信任请求体。催办、重发、抄送及撤销审批申请只产生待发事件。

## 扩展点

每个扩展点是一个接口，加新功能就是写一个实现、在登记处加一行，引擎核心不动（设计书第 10 节）。接口名是建议，实现对应任务时定：

| 扩展点 | 建议的接口 | 初版的实现 | 以后 |
| --- | --- | --- | --- |
| 节点类型 | `INodeBehavior` | 审批、办理、抄送、三种网关、子流程、自动节点 | 等待节点等 |
| 审批人来源 | `IAssigneeResolver` | 设计书第 4 节的 14 种 | 项目成员、HR 系统 |
| 多人审批方式 | `IApprovalPolicy` | 依次、会签、或签、票签 | 新的通过规则 |
| 条件和计算函数 | `IExpressionFunction` | SUM、AVG、MAX、MIN、IF、日期差 | 业务需要的新函数 |
| 自动节点动作 | `IServiceTaskAction` | 调业务系统的 HTTP 接口 | 经 ESB、发消息队列 |
| 消息渠道 | `INotificationChannel` | 邮件、站内消息 | 企业微信、钉钉、App 推送、短信 |
| 事件发布 | `IEventPublisher` | 回调 | 消息总线、ESB |
| 附件存储 | `IFileStorage` | 本地、MinIO / S3 | 平台文件服务 |
| 组织架构来源 | `IOrganizationSource` | 自己维护 + 业务系统推送 | 主数据系统 |
| 登录 | `IIdentityProvider` | 本地账号、嵌入令牌 | 公司统一登录（OIDC） |
| 打印 | `IApprovalPrinter` | 默认样式加配置 | 自定义打印模板 |

引擎相关的扩展点（前四个）定义在引擎核心里，其余定义在应用层、实现在基础设施层。

## 平台化预留

- 所有调外部系统的地方（回调、钩子、自动节点、消息）都经过出站适配层，现在直接发 HTTP，以后改配置走 ESB。
- 现在自己验 API Key 和登录令牌；以后有 API 网关时，可以改成信任网关传来的身份。
- 请求带进来的链路 ID 一路传下去（`RequestTraceMiddleware`，回调和钩子也带）。
- 进程不保存状态；后台任务按“抢锁”执行，换成 SQL Server 或 PostgreSQL 后可以多开实例。

## 数据

- MVP 用 SQLite（数据目录 `ApprovalService:Data:Directory`）；和标签服务一样用 EF Core，三种数据库的迁移都生成，不写某一种数据库特有的 SQL，切换只改配置（`DataOptions`）。
- 部署可选单实例 Linux Docker 或 Windows 服务。`Api/Hosting/RequestMetrics` 以固定路由模板聚合 HTTP 数量和耗时，`/metrics` 默认仅本机访问，远程采集要求部署密钥；不把审批单号或人员写进标签。`Infrastructure/Hosting/SqliteBackupService` 用 `VACUUM INTO` 备份 SQLite 活动库，复制本地附件及登录签名密钥；每日按服务器本地时间执行，发现待执行迁移时先拍升级前快照，失败拒绝迁移。恢复过程与演练见 `backend/deploy/README.md`。
- 审批库和业务库分开：审批服务不连业务库，业务数据只通过接口进出，审批库里只存审批要用的快照。
- 主要数据表见设计书第 9 节。
- `Domain/Runtime` 定义流程、版本、审批单、任务投影、只追加事件、待发项和定时任务；`Infrastructure/Persistence` 为三种提供程序维护同一模型和各自迁移。SQLite 启动时迁移，数据库不可连接时就绪检查返回 503。
- `Application/Runtime` 从固定发布版本加载执行图，把引擎结果、任务投影、事件校验链与待发项交给仓储一次提交。审批单的 `Version` 是乐观锁；并发命令只允许一次推进，重试由调用方重新读取状态。审批单还保存最终事件序号和哈希锚点，以识别事件链尾部删除；审计校验在同一事务快照内读取锚点和记录。
- `Infrastructure/Jobs` 通过数据库条件更新抢占有期限的租约；外部调用在数据库事务外进行。领取后回读核对本次租约，完成或失败回写按实际经过时间检查租约，已过期的旧工作者不能继续处理或确认执行。失败按退避表重新排期，进程重启后继续领取到期项目，处理器由集成模块登记。
- `Application/Notifications` 定义可扩展的 `INotificationChannel` 与传输用例，并按发布节点和部署工作日历在任务实际进入待办时固定 `DueAt`，不重算已有待办的期限；同一审批事务还写入到期前一个工作小时和到期时的延迟提醒。新待办、催办、结果、抄送与提及从实际引擎事件规划，经保密参与人权限及在职人员过滤，与事件同事务固定站内、邮件待发项。`Infrastructure/Notifications` 在期限提醒发送前确认任务仍待办、期限未变化，再通过待发处理器发送 SMTP 邮件，或按稳定消息 ID 幂等保存站内收件箱，支持按人员读取和标记已读。个人类别开关在投递前再次核对；管理员配置当地每日汇总时刻，未配置不安排，收件人每天最多一封。邮件采用至少一次发送语义，稳定的 `X-Approval-Notification-Id` 可供下游去重。
- `Domain/Integration` 保存接入应用权限、API Key 摘要和加密签名密钥；`Application/Integration` 在已认证管理用例中签发密钥，并按应用和流程定义双重授权公开发布流程。审批事务把回调正文固定在待发项里，`Infrastructure/Integration` 经统一签名 HTTP 适配层在事务外发送，5 秒超时、失败交队列退避重试；每次发送单独留不含正文的日志，管理用例重排同一事件时保留事件 ID。出站地址默认要求 HTTPS，只有受信任内网部署显式开启才允许 HTTP；不跟随重定向。接入应用停用时保留回调待发项并记录暂停原因。审批单详情在同一事务快照读取状态、任务和事件；全局在途单号若被其他应用占用，只报告冲突而不泄露内容。开放发起的人员和部门身份只接受本应用既有绑定，选定发起部门还需核对人员归属；流程的部门权限配置只按可信组织主数据解析。持久化流水号使用部署级默认格式，流程级格式由管理后台接入。发起时的业务数据与自选人员映射随审批单保存，后续人工命令推进节点前重新读取最新组织和矩阵；实例与任务操作始终双重核对接入应用归属及实际操作人。四类业务钩子按已采纳的 ADR 0010 使用各应用完整 URL、POST JSON 和双向 HMAC；取数及发起/同意校验在审批写事务前执行，签名以响应原始字节恒定时间核对，请求 ID 必须回显。取人只在纯引擎报告的实际命中节点前调用，返回人员仅按当前应用已有绑定解析；补齐可信快照后按原命令、固定时间与 ID 重算，未完成取人时不提交中间状态。自动节点由事务内固定的 `actionPending` 待发事件触发，后台事务外双向验签调用业务动作，成功后用稳定事件 ID 提交引擎结果，失败由队列退避重试。
- `Application/Administration` 读取安全组织及应用摘要，并通过本地组织管理员授权的 GET/PUT 配置每个应用的允许嵌入来源。来源只接受完整 HTTPS 原点和本机开发 HTTP 原点；`Infrastructure/Integration` 使用旧值条件更新，连同操作人、原因及脱敏前后快照写入组织变更审计事务。`ClientAppAppService` 复用应用登记、启停和密钥轮换规则，管理端入口把实际写入及脱敏审计封在同一事务；创建或轮换的密钥仅在该次响应回传。管理员列表不投影应用密钥字段。
- `Application/Integration/ClientAppAdminAppService` 通过本地组织管理员管理每个接入应用的内部人员 ID 名单，存量默认为空。`Infrastructure/Integration/ClientAppAdminRepository` 在串行化事务中验证目标人员仍在职、按旧值条件替换名单并记录仅含人员 ID 和原因的审计。应用层为后续测试回调提供重新核对本地会话、应用启用、当前在职和本应用管理员或组织管理员的授权查询；管理接口不发送回调。
- `Application/Integration/TestCallbackAppService` 从当前本地人员身份创建独立 `integration.test` 合成通知；`TestCallbackRepository` 在入队事务再次检查应用启用、回调地址、人员在职及本应用管理员或组织管理员资格，并与脱敏原因审计原子提交。待发项使用合成来源 ID，不建立审批单；`CallbackOutboxHandler` 仅对该事件使用正文中的可信接入应用编码，仍走统一签名出站、重试和发送日志。管理待发摘要对测试项提取应用编码，对普通回调继续不装载正文。
- `Domain/Administration` 规定绑定与操作日志的安全查询边界；`Infrastructure/Administration` 分别投影业务系统外部绑定，以及最近 200 条组织/接入应用/回调重发变更元数据。完整审计快照只留数据库，管理 API 不返回快照和联系方式；手工绑定继续由组织应用服务按当前管理员身份写入并留痕。
- 待发队列管理查询只投影最近 200 条待发项状态、次数及错误类别，并通过实例关联已登记应用编码，不读取正文。回调人工重发由本地组织管理员带原因调用原事件重排服务；队列更新和管理员审计在同一数据库事务内提交，业务系统通过稳定事件 ID 去重。
- `Domain/Files` 保存附件元数据抽象，`Application/Files` 统一校验大小、真实类型、身份和审批单可见性；`Infrastructure/Files` 实现本地与 MinIO 内容存储、数据库元数据、孤儿清理和本地到对象存储迁移。文件字节不入数据库；历史附件按元数据中的存储编码读取。未关联附件记录人员或接入应用两种互斥的上传主体，应用只能读取本应用上传的未关联文件；嵌入人员会话不能读取未关联文件。公开附件路由从已验证的 API Key 或人员会话确定上传主体，不信任请求自报的应用编码。发起审批先保存实例与运行记录，再在同一显式数据库事务中按应用归属和未关联状态条件更新每个附件；任何一条未命中即回滚整笔事务，并发发起也不能重复占用文件。普通抄送到达时固定实际收件人，与人工抄送和任务完成的实际处理人一起在运行事务内写历史参与人投影。已关联附件可向发起人、代发人、当前任务人及历史参与人开放；保密版本排除仅有已取消或转交任务的旧指派人，管理员和额外查看人不自动有权；嵌入会话再核对来源应用。

## 前端

- `src/model/`：纯逻辑模块，Node 下能直接运行，`tests/checks.ts` 里检查。
- `src/api/`：调后端接口，统一的错误格式转成 `ApiError`。
- `src/pages/`：页面；`WorkspacePage` 提供尚未接入业务的工作区，不能把未接入误显示为无数据。后续按模块接入独立页面。
- `src/model/routes.ts`、`navigation.ts`：hash 路由与导航元数据；已登记路由严格匹配，未知地址显示未找到页面；手机端使用 `#/m` 独立外壳。导航只代表入口，不是权限控制。
- `src/components/layout/`：桌面/手机外壳，统一顶栏、侧栏、抽屉和底部导航；`src/components/ui/`：公共图标、空状态、原生对话框、子页面错误恢复边界。
- `src/composables/`：导航历史/滚动/焦点与服务连接生命周期；普通导航回到顶部，浏览器历史按条目恢复位置。服务信息重试取消旧请求，卸载后不再更新状态。
- `src/api/`：通用 JSON 请求负责 HTTP/字段错误、状态码/链路信息、超时/取消和响应解析；服务信息入口额外验证响应结构。只发一次请求，不自动重试业务写操作。中心专用会话模块使用本地登录 JWT，令牌只在页面内存保存，到期前轮换；中心适配器逐页请求已授权数据，不使用应用 API Key。
- `src/style.css`、`src/styles/`：沿用标签服务与原型的设计变量和公共样式；不从原型目录跨部分导入文件。
- `tests/`：路由、HTTP 和组件场景检查，加上注释与规模检查；Vue 自带编译器/渲染器仅用于检查，不新增运行依赖。
- `src/designer/canvas/`：统一自由画布使用 bpmn-js Modeler 编辑 BPMN 2.0 常用子集，适配层把图元映射到 Contracts 的前端流程模型；审批属性、静态校验镜像和带本服务扩展的 BPMN 导入导出保持独立。工作台通过模型、选择事件与属性插槽接入；后端仍编译执行图并进行权威发布校验。
- 以后加：`src/stores/`（业务状态）；当前不放演示业务数据。
