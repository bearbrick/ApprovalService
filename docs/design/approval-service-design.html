审批流服务

一个独立部署的审批服务，和标签服务一起组成公司的产品平台。它不产生业务单据，只管审批：画审批流程、按流程流转、记录每个节点谁在什么时候怎么批的。所有审批都由业务系统发起：公司的业务系统（Vue + .NET 10 的 Web 系统和 WinForms 客户端）通过开放接口和 .NET SDK 接入，登录后就能看到有几件待审批、点开直接审批；审批结果回到业务系统，审批单可以直接打印。它按公司产品平台里的一个微服务来设计，引擎和扩展点为以后的平台化留好位置。

1初版范围

审批服务只管审批，不产生业务单据，所有审批都由业务系统发起。两个目标：中国式审批的常见需求尽量一次做全；业务系统接入时改得越少越好，审批相关的事都由审批服务包下来。和平台有关的部分（统一登录、主数据、企业微信和钉钉）先把接口留好，后面接入时不动核心。

初版做

  • 流程：统一自由画布（BPMN 常用子集）；审批、办理、抄送、条件、包容、并行分支、子流程、自动节点（第 3 节）
  • 审批规则：按第 4 节的需求清单全部做，标“二期”的除外
  • 示例业务系统（WinUI 3 界面 + 单独的对接类库）：费用报销、采购申请两种单据，演示对接全流程和业务系统要改多少（第 14 节）
  • 引擎内核和扩展点按平台化要求做：执行图加令牌、操作都是命令、事件留底、可插拔的扩展点（第 9、10 节）
  • 审批数据和详情展示：字段定义、发起时校验、详情排版、摘要字段、审批人填写的字段、节点字段权限、附件（第 5 节）
  • 审批中心（给审批人用）：待我处理、我已处理、抄送我的、我发起的（看进度），批量审批；电脑网页和单独设计的手机网页；邮件和站内消息提醒（第 6 节）
  • 打印审批单：默认样式，每个流程可以调（第 7 节）
  • 统计报表（第 8 节）
  • 附件存储：本地文件和 MinIO / S3 两种，改配置切换（第 9 节）
  • 组织架构自己维护，业务系统绑定、推送变更；账号先独立（第 11 节）
  • 业务系统对接：只提供数据接口（开放接口和 .NET SDK），不提供界面组件；待办数量、免登录跳转和内嵌审批中心页面；接入向导、流程模板库、测试模式（第 12 节）
  • 数据库：MVP 用 SQLite，代码按 SQL Server、PostgreSQL 也能用的方式写，需要时切换
  • 管理后台沿用标签服务的做法：登录、用户和权限、系统信息、操作日志

预留接口，后续接入

  • 企业微信、钉钉：消息卡片、应用内审批、免登录（第 6 节）
  • 公司统一登录：审批服务和标签服务一起接进产品平台（第 11 节）
  • 主数据系统：以后组织架构从这里同步（第 11 节）
  • 安卓、iOS App：原生还是 H5 套壳到时候定，现在把接口、登录、推送留好（第 6 节）
  • 平台公共能力：ESB 统一出口、API 网关、消息总线、平台的消息中心和文件服务（第 10 节）

二期再议

  • 超时自动处理（初版到期只提醒）
  • 多租户
  • 完全自定义的打印模板（初版是默认样式加配置）
  • Office、OFD 附件在线预览（初版图片、PDF 能在线看，其他下载查看）
  • BPMN 里不常用的部分：定时和消息事件、补偿、事务

不做

  • 在审批服务里发起审批、填业务表单：审批服务不产生业务单据，发起都来自业务系统
  • 给业务系统的界面和框架组件（Vue 组件、WinForms 控件、ASP.NET Core 扩展）：只提供数据接口，界面由业务系统自己做，以后需要再讨论
  • 直连业务库：审批库和业务库分开，审批服务只通过接口和业务系统交互
  • 电子签章：暂不考虑（初版有手写签名和签名图片）
  • 导入其他工具画的 BPMN 文件：只导入本系统导出的
范围变化2026-10-13 四次调整：先加入自由画布、委托和票签、统计报表；再补齐中国式审批规则清单和业务系统对接；再按待确认问题的答复，把企业微信、钉钉改为预留、邮件先做，加入待办集成、附件存储、打印样式和两个试点；最后明确审批服务不产生业务单据、发起都来自业务系统，把表单设计器改成“审批数据与详情展示”，去掉在审批中心发起。工作量大约是第一稿的三倍，排期见第 15 节。

2总体架构

服务由管理 API、开放接口、审批中心 API 和流程引擎组成，进程本身不保存状态，初版单实例部署在内网服务器（能访问外网）。和标签服务分开部署、各用各的数据库，技术栈、代码结构、接口风格保持一致，以后一起接入公司的产品平台。

部分选型说明
前端Vue 3 + TypeScript + Vite统一自由画布采用 bpmn-js Modeler 编辑 BPMN 2.0 常用子集，并按许可要求保留可见的 bpmn.io 标志；审批规则和数据定义仍由本服务 JSON、属性面板及后端执行图处理。详情排版设计自己做；手机页面候选 Vant（MIT 协议的 Vue 3 手机组件库，引入时写 ADR）
后端.NET 10，ASP.NET Core领域、应用、基础设施、接口四层，命名和标签服务一致；流程引擎自己写，不用 Elsa、Camunda 这类通用引擎（中国式审批规则要深度定制，套通用引擎反而绕）
数据库EF Core；MVP 用 SQLite和标签服务一样，SQLite、SQL Server、PostgreSQL 三种的迁移都生成，不写某一种数据库特有的 SQL；MVP 只在 SQLite 上测透，需要时改配置切换
附件本地文件或 MinIO / S3统一的存储接口，改配置切换；数据库只存文件信息（第 9 节）
对接开放接口、.NET SDK只提供数据接口，不提供界面组件；公司业务系统都是 .NET，只出 .NET 的 SDK；SDK 兼容 .NET Framework 4.6.1，和标签服务的 SDK 一样不依赖第三方包；公司没有私有包源，先不发布，业务系统按接口对接
网络内网部署，能访问外网发邮件、以后接企业微信和钉钉都只需要往外连；手机网页在公司网络里能直接打开，在外面要走 VPN；以后上 App 要给服务配一个公网入口

3流程设计器

所有流程统一使用自由画布，按 BPMN 2.0 常用子集绘制。简单流程从模板开始，复杂流程直接配置条件、并行、回路和子流程，不再区分画法。节点属性、审批规则、业务数据和发布检查在同一工作台完成。

已确认调整 · 2026-10-13用户要求取消钉钉式设计，一步到位使用自由画布。详见 ADR 0007；执行图和纯引擎架构保持不变。
能力统一自由画布
基本操作拖动节点、连线、缩放和平移、适配视图、对齐吸附、撤销重做；选中节点或连线后在属性面板配置。
常见路径顺序审批、金额与组织条件、会签与票签、并行会审和汇合、条件包容分支、返工重审、子流程、办理、抄送、自动业务动作。
业务人员使用从报销、采购、合同、质量异常模板复制；属性说明提示规则后果；校验问题直接定位对应节点与连线。
条件与汇合条件写在线上，排他分支按优先级命中一条，包容分支可命中多条；显式设置兜底线和配对汇合，避免漏配后卡住。
导入导出BPMN 2.0 文件加本系统扩展信息，只支持本系统导出的兼容版本。原型草稿 JSON 与正式文件明确区分。

导入导出主要用来在测试环境和正式环境之间搬流程，以及给新客户装常用流程；导入时检查文件是本系统导出的、版本兼容，不认的直接提示。

流程管理保存单份带修订号的草稿。发布时校验完整执行图，并核对草稿修订和当前发布版后原子追加不可变新版本；停用只阻止新发起，在途继续使用锁定版本。恢复旧版需重新发布为新版本。兼容 BPMN 导入先预检、仅落草稿；同编码默认冲突，指定目标和预期修订才可覆盖。导出可选草稿或发布版，审计仅记录操作者、原因、版本和内容 SHA-256。

业务系统提交前可以预览流程：按单据数据算出会走哪些节点、每个节点的审批人是谁；发起人要自选审批人时，用选人组件在业务系统里选。流程发布前可以在测试模式里模拟发起，自己扮演每个审批人把整条流程点一遍。

4中国式审批规则

下面按“找审批人、怎么审、自动处理、谁能做什么、意见签名、时限提醒、委托交接、可见范围”列出中国式审批的常见需求，初版全部做，标“二期”的除外。每一条都是流程或节点上的设置，有默认值，管理员可以改；每个节点还能单独设置允许哪些操作（比如某一步不许转交）。

找审批人

来源说明
指定成员写死的人，如“张明”
角色如“财务总监”；可以限定在发起人所在部门里找，如“本部门的文员”
岗位、职级如“经理级及以上”
直属上级发起人的第 1 级、第 2 级……上级
连续多级上级从直属上级逐级往上，直到第 N 级或某个职级为止
部门负责人发起人所在部门的负责人，可以往上数第 N 级部门
业务数据里的部门单据里的部门（如“费用承担部门”）的负责人
分管领导按分管关系找，如“分管生产的副总”
业务数据里的人员单据里的人员字段是谁就是谁，如“项目负责人”
审批矩阵按金额区间、部门、物料类别等查一张表找人；表在管理后台维护，换人不用改流程
业务系统接口调业务系统的接口取人，如“这个项目的项目经理”
上一步指定由上一个审批人选下一步的审批人
发起人自选发起时选，可以限定范围
发起人本人用于“确认”类节点

发起人同时在几个部门时，业务系统发起时带上“以哪个部门发起”（不带就用主部门），上级、部门负责人都按这个部门找。

怎么审、自动处理

设置选项（加粗的是默认值）
多人审批方式依次审批（按顺序一个一个审）；会签（全部同意才通过）；或签（一人同意就通过，其他人的任务自动取消）；票签（同意的达到设定比例就通过，可以给每人设权重；反对的多到已经不可能达到比例时按拒绝处理）
会签中有人拒绝立即结束；等所有人审完再按结果定
找不到审批人不允许发起，提示原因；自动通过；转交流程管理员；转交指定的人
审批人就是发起人自动跳过；由本人审批；转交直属上级
同一人多次出现相邻的只审一次；整个流程只审一次；每次都审
审批人离职或停用转交他的直属上级；转交流程管理员
审批人什么时候算到这个节点时才算，组织调整后按新的算；发起时预览先算一遍给发起人看，到节点时和预览不一样会在记录里注明

流程定义按上述规则保存可选参数：角色限定发起部门、连续上级的截止职级，以及“找不到审批人时转交指定的人”的目标人员。旧流程未设置这些参数时继续使用原有默认行为。

审批人能做的

操作说明
同意、拒绝拒绝时整个审批结束（票签时算一票反对）；可以设意见必填
退回退回给发起人、上一步或之前任一处理过的节点；重新提交后从头走或直接回到退回的节点（流程里设置）；并行分支里只能退回到同一条分支或分叉之前
转交把这一步交给别人处理
加签在自己之前或之后加人，或者加一个人和自己一起审
减签加签的人可以把自己加的人去掉（对方还没处理时）
征询意见请别人给个意见，对方回复后自己再决定，不影响流程走向
要求补充请发起人补材料：回调通知业务系统，发起人在业务系统里补完重新提交，回到自己这里继续审，不用重走流程
抄送审批时顺手抄送给别人
撤销同意自己点了同意、下一步还没人处理时，可以收回
评论、@人留言、加附件，@到的人收到提醒
暂存意见写一半先存着
批量同意待办列表里勾选多条一起同意；流程可以设成不允许批量

发起人能做的（都在业务系统里，由业务系统调接口）

操作说明
发起业务系统调接口发起，可以带上：加急、代发人（如秘书代领导）、发起部门、发起人自选的审批人和抄送人
撤回审批结束前都能撤回；可以设成“第一个人处理前才能撤回”
催办再提醒一次当前审批人，同一步每小时最多一次；审批中心“我发起的”里也能催
补充、重新提交被要求补充或被退回时，回调通知业务系统；发起人在业务系统里改好单据，业务系统调接口带上新数据重新提交
撤销已经通过的单据（如请假）要作废时，业务系统对它再发起一次撤销审批，通过后回调

管理员能做的

操作说明
修改审批人改在途审批单当前或后面节点的审批人
跳转把审批单跳到指定节点（如走错了分支）；不能直接跳到并行或包容汇合网关，避免缺少分支令牌而卡住
终止强制结束，结果是“已终止”
离职交接一键把某人的待办、以及所有流程里写死的这个人，转给接手的人
重发重发提醒、重发回调

管理员的每次干预都要填原因，记进操作记录。

意见、签名和打印

需求说明
意见常用语；按节点设是否必填；意见显示在审批详情和打印的“意见栏”里（如“部门意见”“财务意见”）
签名手写签名（手机上直接写）、个人签名图片，签名跟着意见显示。本人 PNG 不超过 2 MiB，个人签名不会自动引用；每次操作要明确选用并冻结到审计。节点可配置成功推进必签，默认关闭；嵌入会话只能上传单次签名，不能修改个人资产。
打印审批单生成 PDF，含业务数据、每一步的意见和签名；样式见第 7 节
电子签章暂不考虑

时限与提醒

  • 节点可以设处理时限，按工作日的工作时段累计（默认 09:00–18:00；工作日历里维护节假日和调休），从任务实际进入待办时开始计时。
  • 到期前 1 个工作小时提醒、超时提醒，通知审批人和发起人；每日待办汇总邮件由管理员配置发送时间，个人可以关闭，未配置时不发送。
  • 超时后自动同意、自动转交：二期。

委托代理

  • 本人或管理员设置：从什么时候到什么时候、委托给谁、范围（全部流程或指定流程）。
  • 期间新到的任务直接给代理人，审批记录写成“王强（代张明）”；张明自己也能看到、也能处理。已经在手上的待办可以选择一并转给代理人。
  • 不连环委托：张明委托王强、王强又委托了别人时，张明的任务只到王强，避免绕圈。
  • 代理人恰好是发起人时，按“审批人就是发起人”的设置处理。

可见范围与分级管理

  • 谁能用：每个流程设定哪些接入应用能用它发起，可以再限定发起人的部门、角色、岗位。
  • 谁能看一张审批单：发起人、参与人、抄送人；另外可以按流程设查看人，如部门负责人能看本部门发起的。
  • 保密流程：发布版本可选标记，旧版默认非保密。只有发起人、实际代发人、实际任务处理人和已送达抄送收件人能看，历史参与人继续可见；管理员和额外查看人不自动有权，统计里只显示数量。
  • 分级管理：各部门的流程管理员只管自己的流程。
留痕每一次操作都记进操作记录（谁、代谁、什么时候、做了什么、意见、管理员干预的原因），只追加、不修改；每条记录带上一条的校验值，被人改过能查出来。

5审批数据与详情展示

审批服务不产生业务单据，也不提供给发起人填的表单：单据在业务系统里创建、修改、保存，提交时把审批要用的数据传过来。审批服务这边只定义“要传哪些数据”和“审批人看到的样子”，做法和标签服务的“数据源定义”一样：只定义 key 和类型。

能力说明
审批数据定义每个流程定义业务系统要传的字段：key、名称、类型（文本、数字、金额、日期、人员、部门、附件、明细表）、是否必传。用来判断条件、找审批人、显示摘要和详情、打印
发起时校验按定义检查业务系统传来的数据，缺字段、类型不对时拒绝发起，并说明是哪个字段（和标签服务的 FIELD_REQUIRED 一样）
计算字段如“合计 = SUM(明细.金额)”，只用于判断条件和显示，不回写业务单据；业务系统已经算好的直接传
详情排版审批人看到的样子：自动排版（按字段生成，零配置）；或者拖拽排版：分组、一行几列、明细表的列和列宽、金额旁显示人民币大写；也可以直接嵌入业务系统的原单页面（第 12 节）
摘要字段选 3～5 个关键字段，在待办列表、角标弹出的列表、邮件里直接显示
审批人填写的字段有的节点要审批人填一点东西，如财务审核填“核定金额”、出纳填“付款日期”；填的内容记在审批记录里，随回调带回业务系统，由业务系统决定怎么更新单据
节点字段权限每个节点可以隐藏某些字段（如成本价只给财务看）
附件业务系统发起时把附件一起传过来（如报销票据），审批服务存一份，审批人在线看、打印时附票据页；审批人在意见里也能加附件
审批编号每次审批一个编号，如 SP-202610-0007，前缀、日期格式、流水号位数可以配；业务单号由业务系统自己管
  • 发起时保存一份业务数据快照，审批人看到的是提交时的数据。业务系统确实要在审批中改数据时走接口，改动留痕并标给审批人看（第 12 节）；只允许修改发布版本显式开启“审批中业务更新”的字段（缺省关闭），服务重算公式和后续路由，已到达任务不静默改派。
  • 条件网关在实际到达时按当前业务数据与成功提交的审批人填写字段求值。本次成功处理填写的字段可决定紧随其后的分支；发起时尚未填写的审批人字段不预先选择路径，退回重提时不沿用已清空的旧值。测试模式的假任务也按相同规则填写假字段并求值。
  • 计算字段用自己写的表达式解析，只支持四则运算、比较、常用函数（SUM、AVG、MAX、MIN、IF、日期差等），不执行任意代码。
  • 这份设计里的“审批单”指一次审批的记录（流程实例），不是业务单据。

6审批中心、手机端与提醒

审批人在哪里方便就在哪里审：电脑上的审批中心、手机网页，或者业务系统里内嵌的审批窗口（第 12 节）；以后还有安卓、iOS App。几个入口用的是同一套接口。

审批中心

详情的流程图由现有 BPMN 查看器显示已到达路径并高亮当前节点；未来节点和连线条件不会下发给当前查看人。征询回复、减签和同分支退回的目标只列当前任务可选项，提交时引擎再次核验。“我发起的”详情可催办当前审批人，同一步每小时最多一次；页面操作后按服务端待办总数刷新角标。已授权 PDF 附件在本地 blob: 地址预览，原单 iframe 的网络来源仍仅限应用登记的 HTTPS 来源。

  • 列表：待我处理、我已处理、抄送我的、我发起的（只看进度）；按流程、时间、状态筛选，按标题、编号、字段内容搜索；加急的排前面，未读的加粗。
  • 列表里直接显示每个流程的摘要字段（如金额、供应商、事由），不点开也能判断；可以勾选多条批量同意。
  • 详情页：业务数据（按详情排版显示，或嵌入业务系统的原单）、意见栏、流程进度（时间线，加上流程图里标出走到哪一步、谁在处理），以及当前能做的操作按钮；附件里的图片、PDF 在线看。
  • 打印审批单：一键生成 PDF（第 7 节）。
  • 审批中心不能发起审批，也不能改业务数据；这里只做审批、看进度、设置委托代理、维护自己的签名和常用语。

个人常用意见按登录人员保存在审批服务中，每人最多三十条、每条最多五百字。本地登录可维护，嵌入会话可只读选择；选择只填入审批意见栏，提交仍须由审批人确认并走现有任务操作接口。

个人委托规则按 UTC 左闭右开时段和流程范围保存，空范围代表所有流程；同一委托人有交叠的时间和流程范围时拒绝保存。本地登录人员可管理本人规则，组织管理员可代指定人员管理；嵌入会话只读。新任务到达时按当前规则只解析一层代理，原审批人仍保留处理权；本人或管理员可选择已经在手的任务逐项转委托，管理员须写原因并以真实操作人留痕。删除规则只影响未来任务，不撤销已经转出的任务。

已实现的中心接口使用登录 JWT：按实际人员参与关系查询待办、已办、已送达抄送、发起或代发记录；嵌入会话同时限定来源应用。授权过滤先于计数和分页，保密详情不会因管理员身份或尚未到达、已取消的任务自动开放。响应按节点权限隐藏业务字段和明细列，不返回内部状态、原始审计正文或私人暂存意见；无权详情与不存在统一返回 404。桌面页面现可用本地工号密码登录并读取四类真实列表及详情，首次登录先改密；令牌仅在当前页面内存保存。列表摘要和详情的可见字段带有锁定发布版本的名称与种类，隐藏字段和明细列的名称不会返回；页面将明细绘成只读表格，自定义详情分组和列宽也只按可见字段裁剪，金额大写由服务端计算，部分隐藏分组使用通用标题。原单嵌入模式按当前人员调用业务系统第五个签名钩子，只接受不超过五分钟、来源已登记的 HTTPS 只读临时地址；业务系统负责一次性、人员绑定、隐藏字段裁剪和禁止写操作，无法显示时回退已授权普通详情。可见附件字段中的文件须仍关联本审批单才列入详情，下载及图片/PDF 预览经独立文件权限接口读取，Office 文件只下载。服务端从当前运行状态和锁定发布图返回逐任务可操作命令及可批量同意的实际任务 ID；页面按许可显示操作并提交，写入时再次检查人员、应用、节点和字段权限，最后经统一引擎持久化。批量同意逐项独立返回结果。当前支持标题、审批编号、业务单号及当前人员可见字段内容搜索；服务端先按参与关系与嵌入应用授权，再按锁定版本的节点隐藏规则裁剪字段与明细列，最后计算命中数和分页，隐藏字段与未定义键不能经搜索泄露。列表未读按人员和审批单的持久活动游标判断，列表读取本身不改状态；详情成功显示后显式标记，本人操作与私人草稿不触发本人未读，其他人的新可见活动会重新变未读。

审批中心前端构建物由审批服务同源托管。普通页面和直接静态 HTML 默认禁止 iframe；专用地址 /embed/{clientAppCode} 仅允许该应用登记的网站来源嵌入，生产环境缺少构建入口时服务拒绝启动。路径中的应用编码只决定页面安全响应头，不授予人员权限。业务后端签发的一次性令牌放在 URL 片段中，页面立即清除并兑换；后续中心请求以嵌入 JWT 重验人员、应用、绑定和身份代际。仅嵌入会话能从 GET /api/v1/center/embed-context 读取自身应用的允许来源，完成消息只发往与页面来源严格匹配的登记网站。

8统计报表

回答三个问题：审批慢在哪个流程、卡在哪个节点、压在谁手上。报表按管理范围看数据：部门负责人看本部门，管理员看全部。

角度看什么
流程发起量、通过率、拒绝率、撤回率，平均耗时和 90% 的审批在多长时间内办完，按周、月的趋势
节点每个节点平均停留多久、超时率，找出最慢的节点（瓶颈）
人员、部门手上积压的待办、平均处理时长、超时次数、处理量

可以按时间段、流程、来源业务系统、部门筛选，导出 Excel；审批单列表也能按条件导出明细（含审批数据里的字段）。定时任务每小时把已结束的任务汇总进统计表，报表查汇总表，不扫明细；当天未汇总的部分实时算。

已接入四条本地 JWT 报表 JSON 查询、同范围的 Excel 汇总导出及管理后台报表页面：概览、流程、节点和人员。组织管理员可看全部，部门负责人仅看直接负责部门，不自动包含下级；部门归属以发起时快照为准。发起量按发起时间，结束量和历时按结束时间，筛选区间为 UTC 左闭右开；P90 只取已结束审批单，逾期率分母为已到期任务。保密流程仅计入匿名发起量和结束量，不输出流程、节点或人员明细；导出时保密量只放在独立匿名表。页面提供时间、流程、来源应用与部门筛选；小时汇总、趋势与逐单明细导出仍按本节后续建设。

引擎内核（要做扎实的部分）

做法说明
执行图 + 令牌运行时用“令牌”标记走到哪：并行分叉生出几个令牌，汇合时等齐；包容网关只等真正走了的分支；回路、子流程都用同一套机制。自由画布及以后扩展的节点都跑在这一套上
操作都是命令同意、拒绝、退回、转交、加签、撤回、跳转……每个操作是一条命令：引擎检查能不能做 → 改状态 → 产生事件，一个事务写完。审批中心、开放接口、管理员干预、定时任务都走这一个入口，规则只写一处
事件留底每条命令产生的事件写进操作记录（只追加、带校验值）；回调、消息、统计都从事件来，出了问题能按事件重放、核对状态对不对
幂等命令带请求 ID，网络重试、连点造成的重复提交只生效一次
定时不丢到期提醒、失败重试这类定时任务存在数据库里，服务重启不丢
引擎独立引擎核心不依赖数据库和 Web 框架；预览流程、测试模式直接在内存里跑同一个引擎，结果和正式运行一致
测试第 4 节需求清单每一条至少一个场景测试；另外随机生成流程图和操作顺序反复跑，专门找卡死（令牌永远等不齐）、重复推进这类问题
版本兼容流程定义带格式版本号，老版本的流程一直能跑；以后可以把在途审批迁到新版本（节点对得上的才允许，二期）

状态

  • 审批单：审批中 → 已通过 / 已拒绝 / 已撤回 / 已终止；被退回或被要求补充时是“待发起人处理”；已通过的单子撤销成功后是“已撤销”。
  • 任务（每个审批人一条）：待处理 → 已同意 / 已拒绝 / 已退回 / 已转交 / 已取消（比如或签时别人已经同意）。

几个关键做法

  • 版本锁定：发起时记住流程的版本号，这张审批单一直按这个版本（包括审批数据定义、详情排版和打印设置）走。改流程只影响以后发起的。
  • 不重复发起：“流程编码 + 业务单号”在进行中的审批里唯一，业务系统重复调用会拿到已有的那张。
  • 并发：会签、或签、票签时几个人同时点同意，用乐观锁保证节点只往下推一次。
  • 不在事务里等外部系统：校验钩子在写数据库之前同步调用（有超时）；自动节点、回调、消息都写进待发队列，由后台任务去调，业务系统慢或者挂了不会拖住审批。
  • 防死循环：自由画布允许回路，一张审批单累计推进超过上限（初定 200 步）就停下，标记异常交给管理员。
  • 不丢：回调、自动节点、消息失败按 1 分钟、5 分钟、30 分钟、2 小时……重试，管理后台能看发送记录、手动重发。
  • 性能（初定）：发起、审批接口 P95 ≤ 300 ms（不含业务系统钩子的耗时）；待办数量接口 P95 ≤ 50 ms（业务系统登录时调）；待办列表 P95 ≤ 500 ms；回调正常情况下 1 分钟内送达。

数据库

  • 审批服务用自己独立的数据库，不和业务系统共用，也不连业务系统的库；业务数据只通过接口进出。
  • MVP 用 SQLite（单文件、免安装），沿用标签服务的每日备份和升级前快照：在线快照包含主库、本地附件和登录签名密钥，迁移前快照失败则停止升级；部署环境中的加密主密钥另行保管。
  • 和标签服务一样用 EF Core，SQLite、SQL Server、PostgreSQL 三种的迁移都生成，代码里不写某一种数据库特有的 SQL；切换只改配置。MVP 只在 SQLite 上测透，切换前补跑另外两种的检查。

附件存储

  • 两种存储，改配置切换：本地文件（数据目录下按年月分文件夹）；MinIO 或其他兼容 S3 的对象存储（地址、桶、访问密钥）。另有一个迁移命令，把已有文件从本地搬到 MinIO。
  • 数据库只存文件信息：文件名、大小、类型、SHA-256 校验值、存在哪里、属于哪张审批单；文件内容不进数据库。
  • 上传：业务系统发起前先传附件拿到文件 ID，发起时在数据里引用；审批人在意见里加的附件也一样；限定类型和大小（默认单个 20 MB，可以改），按文件内容判断真实类型，不只看扩展名。
  • 下载：先查权限，能看这张审批单的人才能下载。MinIO 能被浏览器直接访问时，签发几分钟有效的下载地址，否则由服务转发。
  • 上传了但 24 小时内没被任何审批单用到的文件，自动清理。
  • 备份：本地存储时附件目录和数据库一起备份；MinIO 用它自己的多副本和备份。

10可扩展与平台化

最终目标是公司的产品平台，审批流服务是平台里的一个微服务；统一登录、主数据、ESB 统一出口这些以后再做。现在不做，但设计上先把位置留好：扩展功能时只加实现、不改引擎核心，接入平台时只换配置和适配层。

扩展点

每个扩展点是一个接口：加新功能就是写一个新实现、在登记处加一行，引擎核心不动（和标签服务加新元素、新输出格式的方式一样）。

扩展点初版的实现以后可以加

审批人来源第 4 节的 14 种新的人员规则，如项目成员、HR 系统
多人审批方式依次、会签、或签、票签新的通过规则
条件和计算函数SUM、IF、日期差等业务需要的新函数
自动节点动作调业务系统的 HTTP 接口经 ESB 调用、发到消息队列
消息渠道邮件、站内消息企业微信、钉钉、App 推送、短信、平台消息中心
事件发布回调消息总线（如 RabbitMQ、Kafka）、ESB

打印默认样式加配置自定义打印模板（复用标签服务的设计和渲染）

作为平台里的一个微服务

  • 边界清楚：自己的库、自己的接口；别的服务不直接读审批库，审批服务也不读别人的库，只通过接口和事件交互。
  • 接口规范统一：/api/v1 带版本号、OpenAPI 文档、统一的错误格式和 traceId，和标签服务一致；以后整个平台按这一套定规范。不兼容的改动升版本号（v2），老版本保留一段时间。
  • 出口统一：所有调外部系统的地方（回调、钩子、自动节点、消息）都经过一个出站适配层。现在直接发 HTTP；以后有 ESB 统一出口，改配置走 ESB，引擎不动。
  • 入口能放到网关后面：现在自己验 API Key 和登录令牌；以后有 API 网关时，可以改成信任网关传来的身份，两种方式都支持。
  • 事件能接消息总线：审批事件现在用回调发给业务系统；事件发布做成可替换的，以后可以同时发到消息总线或 ESB，让平台里别的服务订阅。
  • 链路追踪：请求带进来的 traceId 一路传下去（回调、钩子、自动节点也带），以后平台能统一看一笔业务经过了哪些服务。
  • 公共能力可以搬走：账号、组织架构、消息、附件现在是服务里的模块，各自隔在接口后面；平台有了统一认证、主数据、消息中心、文件服务后，换成调用平台服务。
  • 能横向扩展：进程不保存状态；后台任务（发回调、发消息、定时提醒）按“抢锁”执行，同一件事只有一个实例在做。MVP 单实例加 SQLite；换成 SQL Server 或 PostgreSQL 后可以多开几个实例。
  • 部署：健康检查、指标（/metrics）、配置方式和标签服务一样，可以用 Docker 部署。
  • 多租户（现在不做）：以后真要做，优先一个租户一个库；现在不在表里加租户字段，不给眼下增加复杂度。

代码结构

  • 沿用标签服务的四层结构（领域、应用、基础设施、接口），另外把引擎核心单独放一个项目：只有流程执行的逻辑，不依赖数据库、Web 框架和任何外部系统。
  • 按业务分模块：流程设计、审批运行、组织架构、账号、消息、附件、对接（接入应用、回调、钩子）、统计。模块之间只通过接口调用，以后哪个模块要拆成独立服务（如消息中心、文件服务）都好拆。
  • 契约（接口模型、错误码、事件格式）单独一个项目，SDK、组件按它同步，和标签服务的契约做法一样。

11组织架构与账号

长远看，组织架构由公司的主数据系统统一管理、登录由公司统一登录负责。现在这两样都还没有，业务系统里的组织数据也不全，所以审批服务先自己维护一套，业务系统通过“绑定”关联；接口按以后要接平台的方式留好。

现在以后（产品平台）
组织架构审批服务自己维护：管理后台编辑、Excel 导入主数据系统统一管理，审批服务改成只读同步
业务系统把自己的用户、部门绑定到审批服务的人员、部门；有变更时调接口推送和主数据对齐，不用再单独推送
账号登录审批服务自己的账号（工号 + 密码）；从业务系统进来用嵌入令牌，不用再登录公司统一登录，审批服务和标签服务一起接进去

组织架构

  • 维护内容：部门树（负责人、分管领导）；人员（工号、姓名、手机、邮箱、岗位、职级、直属上级、在职状态，可以在多个部门）；角色。
  • 初始化：用 Excel 模板导入部门、人员、上下级；导入前先检查（工号重复、上级不存在、上下级绕成圈），有问题列出来改完再导。
  • 绑定：每个接入应用一张对应表，业务系统的用户 ID 对应审批服务的人员，部门 ID 对应部门。绑定方式：按工号或手机号自动匹配、Excel 导入、接口推送、管理后台手工补。绑定后，业务系统调接口时直接用自己的用户 ID 和部门 ID。
  • 推送变更：业务系统（以后是主数据系统）调接口推送人员、部门的新增、修改、调岗、离职。离职时提醒管理员做离职交接，在途的待办按“审批人离职”的设置处理。
  • 谁说了算：人员、部门这类数据指定一个可信来源（现在是审批服务自己），其他业务系统推送的只更新绑定关系和补充字段，不覆盖可信来源的数据，避免几个系统互相改乱。
  • 组织架构的每次改动留记录（谁、哪个来源、改了什么），算审批人时有疑问能查当时的组织。

初版接口提供 CSV、XLSX 模板与导入前预检查；同一模板可导入部门、人员、所属关系和每个接入应用的外部人员、部门 ID 绑定。文件上传上限 5 MB，Excel 最多 10,000 行。接入应用的 API Key 只能推送和绑定本应用来源的数据；跨来源绑定须由本地组织管理员确认。正式导入与推送在可串行化事务中按当前数据重新校验，每项改动在同一事务留下操作者、来源和前后快照，离职时生成交接提醒。

流程管理员 ID 统一为内部人员 ID，流程可选一个直接所属部门。当前在职本地组织管理员管理全部流程；持流程管理员角色的在职本地人员仅管理自己直接加入的所属部门流程，不继承上级部门权限。流程上填写的管理员 ID 用于运行期找人，不直接授予设计权限。历史管理员标识只在人员 ID 或工号唯一匹配时自动修正，无法唯一确认的保留待人工处理记录。

账号

角色管理已提供本地组织管理员专用目录、创建、名称及成员维护。名称和成员共用递增修订，修改必须填写原因并原子审计；新增成员须在职，禁止移除最后一位已开通账号且在职的组织管理员。组织管理员和流程管理员为内置角色，所有角色的编码创建后固定且首版不提供删除。角色变化后权限从持久数据立即重查。管理接口为 GET/POST /api/v1/admin/roles、GET/PUT /api/v1/admin/roles/{code} 及 GET/PUT /api/v1/admin/roles/{code}/members。

空库的首位组织管理员由部署人员在服务器本机控制台运行一次性命令开通：输入人员 ID、工号、姓名和临时密码，也可选用已导入的在职人员 ID。人员、需首次改密的账号及组织管理员角色在同一串行化事务中写入；已有管理员角色时命令拒绝再次执行，不开放匿名 HTTP 初始化接口。

  • 现在独立：人员开通账号后用工号和密码登录审批中心，首次登录要改密码；登录、改密码、权限沿用标签服务的做法。
  • 从业务系统进来不用再登录：业务系统后端用 SDK 签发嵌入令牌（几分钟有效，绑定用户和接入应用），打开待办、审批页面就是这个人。
  • 手机网页和以后的 App 用同一套登录令牌：短期访问令牌加刷新令牌，可以记住登录；手机丢了，管理员可以在后台把这个人的令牌全部作废。
  • 为统一登录预留：登录这一层按标准协议（OIDC）设计，公司统一登录上线后，审批服务和标签服务作为它的客户端接进去，账号按工号对上；到时候可以关掉本地密码登录。

初版访问令牌有效 15 分钟，刷新令牌有效 30 天并逐次轮换；连续 5 次密码错误暂时锁定 15 分钟。首次登录令牌只能用于改密。嵌入令牌由有效 API Key 为本应用已绑定且已开通本地账号的业务人员签发，5 分钟内只能交换一次，不按全局工号回退；嵌入会话及其刷新令牌保留应用和业务人员来源，应用停用或改绑即失效，不能获得组织管理权限。接入应用启停或轮换密钥时应用身份代际单调递增，旧嵌入访问、刷新和未兑换令牌在重新启用后仍无效，本地登录不受影响。可信人员离职、复职及外部人员绑定换人时，旧账号令牌代际不可恢复，尚未兑换的嵌入令牌也按签发代际核验。组织管理员权限以本地登录会话和当前组织角色共同核对。

管理后台的本地登录和首次改密已接入；当前可按组织管理员权限读取部门、人员和接入应用安全摘要，并通过 Excel/CSV 文件预检后正式导入组织数据。管理列表不回传联系方式、API Key 摘要或签名密钥；已接通接入应用登记、启停和密钥轮换，密钥仅在创建或轮换响应中显示一次，实际写入附原因及脱敏审计。尚未接通的其它管理写入保持禁用。

接入应用的允许嵌入来源已可由本地组织管理员读取和保存：提交最多 20 个完整 HTTPS 网站来源，本机开发可用 HTTP localhost 或 127.0.0.1，禁止路径与通配符。保存时填写变更原因，实际修改在同一事务中记录管理员和不含密钥的前后来源快照；其它未接通的管理写入仍禁用。

业务系统绑定页已可按本地组织管理员权限读取人员与部门外部 ID 映射，并手工指定内部目标；换绑时旧人员会话失效。操作日志页读取最近 200 条组织及接入应用变更的安全元数据与显式原因，不向网页传完整审计快照；其他类型的管理日志仍随相应写入功能接入。

待发队列页已可读取最近 200 条事件的安全状态摘要。组织管理员可按原事件 ID 带原因手动重发回调，原正文不经管理页面，重排和操作者审计在同一事务完成；正在发送的有效租约不允许重排。

12业务系统对接

公司的业务系统都是 .NET：Web 系统是 Vue 前端加 .NET 10 后端，另外还有 WinForms 客户端。审批服务给业务系统只提供数据接口（开放接口和 .NET SDK），不提供界面组件：待办角标、审批窗口这类界面由业务系统自己做，或者直接跳转、内嵌审批中心的页面。示例业务系统把这些界面做了一遍，给业务系统照着改（第 14 节）。目标是业务系统改得越少越好。

分工业务系统管单据：创建、修改、保存、作废和单据状态都在业务系统里；审批服务管审批：流程、谁来审、审批记录。发起、撤回、重新提交都由业务系统调接口，审批服务不产生业务单据。
库分开审批服务用自己的数据库，不连业务系统的数据库；业务数据只通过接口进出（取数接口、回调、钩子），审批库里只存审批要用的快照。
业务系统不用做审批流程和规则、审批详情页面、待办列表、消息提醒、手机审批、审批记录、打印审批单、统计报表，都由审批服务提供。

当前发起接口要求已授权流程和本应用已绑定的在职发起人；可直接传审批数据快照，未传时由本应用登记的取数钩子取得。服务端按发布版本校验、重算公式与条件，调用已配置的发起校验钩子，再交统一引擎入口原子保存审批单和在途唯一键；业务钩子拒绝或故障时不写部分审批。顶层和明细附件须由该应用预先上传；发起时去重，并在同一数据库事务内按应用归属与未关联状态有条件地关联到新审批单。任一附件不存在、属于其他应用或已被占用，整笔发起回滚。同一应用的在途同号返回原审批单，其他应用占用同号只返回冲突。编号目前用可配置的部署级前缀、日期格式和流水号位数，数据库分配时保证不重号；流程级编号配置待管理后台接入。取人仅在引擎实际到达业务取人节点时调用，业务人员只按当前应用已有绑定解析，失败不写部分审批状态；自动动作先固定待发事件，审批事务提交后由后台调用，并以同一事件 ID 幂等回写结果。未配置的矩阵流程会给出可纠正错误。

撤回、催办、终止和人工任务操作已接通：业务系统 Key 只能操作本应用审批单，实际操作人必须是本应用已绑定人员；撤回/催办只能由发起人发出，终止必须提供原因。任务 ID 可能包含斜杠，放入 URL 时需编码。引擎继续核对节点权限、任务处理人及意见要求。发起自选人员和业务数据找人 ID 保存为固定快照；后续节点到达按最新组织与矩阵重新找人。

人工任务操作可选传 fieldValues 对象填写顶层审批人字段；字段须在锁定流程定义中标为 approverInput，且当前节点明确授予 editable 权限。字段类型和本应用人员、部门绑定在服务端核对；明细子字段缺少行索引协议、附件缺少归属校验时明确拒绝。已核准值进入操作记录和相关回调的独立 fieldValues，不覆盖原业务数据 data，由业务系统决定回写。当前节点显式可写且标记必填的顶层审批人字段，只在同意、办理完成、确认已阅等成功推进时强制填写；拒绝、评论、暂存与协作操作不强制填写，提交的值仍须通过类型与授权校验。

征询回复须引用原发问任务与征询 ID，受询人只能提交意见，不能借其他任务的字段权限填写审批人字段；原发问任务完成后即使其他节点仍在运行，也不能补交征询回复。退回发起人和要求补充分别发 instance.returnedToInitiator、instance.supplementRequested 回调，均保存当时的 awaitingInitiator 状态和独立的审批人填写值；待发正文固定，重试保持原事件 ID 与正文。

所属业务系统以已绑定原发起人提交完整新数据时，审批服务按锁定版本重新校验字段和公式、刷新可信找人映射，再原子恢复审批。退回重提按发起时固定的策略从头或原节点继续，并清空审批人填写字段的当前值；要求补充恢复原任务且保留当前值。历史操作记录始终保留。审批单详情把当前审批人填写值放在独立的 approverFieldValues，不覆盖业务 data。

业务系统按需提供的接口

都由审批服务的后端调用，带签名，默认 5 秒超时。都不是必须的，用到哪个功能才提供哪个。

已采纳的 ADR 0010 规定各接入应用分别配置四个完整 URL，以 POST 发送小驼峰 JSON；请求与响应正文均按原始字节使用同一密钥计算 HMAC-SHA256，业务系统须回显请求 ID，审批服务验签后才解析响应。取数请求含流程编码、业务单号和请求 ID，返回 data 对象及可选标题、详情地址；校验请求含 phase、业务身份、操作人和数据快照，返回 allowed 以及拒绝原因。取人只接受当前应用已有的在职人员绑定，不按全局工号回退；业务动作由事务提交后待发队列调用。

业务动作成功响应可带 result：审批服务以原动作事件 ID 独立留痕，在后续审批终态回调的可选 actionResults 中带出，绝不覆盖审批数据 data。同一动作事件的回调重发保持首次固定正文。

自动动作失败按退避间隔最多自动尝试十次；达到上限后保留原事件和等待令牌并转为待管理员处理，后台暂停自动领取。当前本地登录的流程管理员可对自己管理的流程调用 POST /api/v1/admin/actions/retry，以 {eventId} 手动重试一次；仍失败则继续待处理。组织管理员角色不会自动获得其他流程的管理权。

14示例业务系统与试点

用一个示例业务系统把对接全流程跑一遍：界面用 WinUI 3 写，秀一下 Fluent 风格；对接代码单独放一个类库，业务系统照着抄。采购申请、费用报销两种单据都从它提交。它有两个用处：试点时当发起方；给其他业务系统看“接一个审批要改多少代码”。

WinUI 3 客户端与对接原型

客户端采用独立的桌面导航、业务单据和待办窗口；既演示自己画审批界面，也演示 WebView2 内嵌审批中心。打开 WinUI 3 客户端交互原型，查看费用报销、采购申请、待办、连接同步与对接说明。此处是 HTML 界面评审，不是已完成的 WinUI 程序；真实 SDK、令牌交换、回调验签和客户端打包按调用端任务实现。

依赖方向固定为 WinUI 界面 → 对接类库 → .NET SDK → 审批服务 HTTP 接口。对接类库承载业务数据转换、状态回写和回调处理，界面只负责输入与展示。有业务后端时由后端接收回调，无业务后端时打开单据查询并定时刷新；两种模式都在原型中标明。

示例系统有什么

  • 界面用 WinUI 3（.NET 10，Windows 10 以上）：云母背景、导航栏、卡片式单据列表、彩色状态标签、自己画的审批进度时间线、跟随系统的深浅色、审批完的提示用通知条。打包成免安装的，自带运行时，拷过去就能跑。
  • 对接代码和界面分开：调审批接口、处理回调、取数、钩子这些代码放在一个单独的“对接类库”里，不依赖 WinUI，能在 .NET Framework 4.8 上编译。WinForms、Web 后端的业务系统直接照抄这个类库，界面换成自己的就行。
  • 直接引用 SDK 项目，不经过包源。SDK 在 .NET Framework 上能不能用，由 SDK 的检查程序和对接类库在 net48 下编译、跑一遍来保证（WinUI 3 本身跑不了 .NET Framework）。
  • 两种单据：费用报销单、采购申请单。列表、新建、编辑、提交审批、撤回、看进度、打印审批单；单据上显示审批状态和审批人填的字段（如核定金额、采购订单号）。
  • 切换当前用户：模拟不同员工登录（申请人、上级、财务……），一台电脑上就能把整条流程审完。
  • 待办角标、待办列表和审批窗口都是示例系统自己画的（调数据接口）；另外演示内嵌审批中心页面（WinUI 3 自带的 WebView2），两种做法都能看到。切到谁，就显示谁的待办。
  • 本机业务后端：示例系统里带一个很小的本机 HTTP 服务，扮演业务系统的后端：取数接口、取人接口（项目经理）、校验钩子（预算够不够）、业务动作接口（生成采购订单）、接收回调。
  • 两种状态同步都演示：有后端的系统用回调；没有后端的 C/S 系统关掉本机服务，改成打开单据时查一次状态、列表定时刷新。
  • 一键准备演示环境：推送演示用的组织架构和人员绑定，导入两个流程（本系统导出的流程文件）。
  • “对接改动”页：列出对接类库里的每一处代码（哪个文件、干什么、多少行），也就是业务系统要加的东西。
  • 自检：带 --smoke，直接调对接类库把下面的演示场景自动跑一遍（不经过界面，方便放进验证脚本）；界面另外截图检查。
注意示例里 API Key 放在客户端配置里，只是为了演示方便。正式的 C/S 系统建议经过自己的服务端调审批接口，或者给每个客户端单独发 Key、限定只能用哪些流程。
